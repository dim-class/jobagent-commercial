# AI 求职助手 · Local AI Job Agent (v1.0)

本地运行的 AI 求职助手：解析简历 → 录入岗位 JD → 用 OpenAI 做匹配分析 →
给出 0-100 匹配分、优劣势、风险与一条中文招呼语 → 在本地看板里跟踪状态。

数据全部存在本机 SQLite，API Key 只存在于后端进程。

> **第一次安装、或者要给别人试用，看 [SETUP.md](SETUP.md)。** 那份是从零到跑通
> 的完整步骤，包含账号风险说明、扩展安装、以及最容易踩的两个坑（改了代码要重新
> 加载扩展、改了后端要重启）。下面这份 README 是完整的开发与功能文档。

### 本地控制台启动 BOSS 采集（0.1.7 M4g live 已通过）

在安装 JobAgent 扩展的正常 Chrome 打开 `http://127.0.0.1:5173/#/console`。
Reload 扩展并刷新控制台一次后，可填写城市/关键词、准备计划，选择 pending 任务，
确认候选上限并点「开始免费采集」。无需先打开 BOSS 或插件弹窗；扩展在同一 Chrome
窗口打开前台 BOSS 标签页，执行现有有限搜索/滚动/详情核对/统一入库。
最多 20 个候选尝试、5 次滚动；本入口不启用 AI 匹配，不投递、不收藏、不发消息。
仍需 Chrome/BOSS 保持前台与有效登录态；登录或验证码需要本人处理。返回控制台可
刷新状态或暂停/取消，恢复沿用原标签页与剩余额度。P3A 综合搜索可在一次页面内确认中绑定

取消或验证会停止/暂停整批。浏览器或 worker 重启后不会自动恢复。
控制台点击不授予 Chrome 截图权限，特殊字体薪资 OCR 可能不可用；不申请所有网站权限。

```
手动粘贴 JD   ──┐

（粘贴/截图） ──┤
浏览器采集    ──┘

岗位 + 简历   ──► JobMatchAgent ──► AI 推荐（0-100 分 + 结论 + 招呼语）
                                    │
                                    ▼
                             投递队列（你来决定）──► 投递 / 跳过 / 稍后
                                    │
                                    ▼
                        HR回复 → 面试 → Offer（全部由你手动记录）
```

**明确不做**：无人值守投递、批量投递、自动打招呼、自动翻页、批量抓取、绕过验证码或反爬机制。
**没有全局自动投递模式**，AI 只负责推荐。M6 仅允许你为一个岗位明确接受 BOSS 将发送
JobAgent 无法预览、核实或控制的动态首次招呼语，经过两次人工确认后尝试一次“立即沟通”；
不批量、不后台、不自动重试，也不发送后续消息。

**v1.0 新增：Offer 决策分析**——多个 Offer 同时在手时，按**你自己设定的权重**
算出综合评分，并把每一步算式（各维度得分 × 权重 = 贡献）完整展示出来。
**不调用 AI**，也不会替任何一家公司打分 —— 主观评分只有你能填。
数据不足时它会明确说「暂不给出结论」，而不是硬凑一个排名。

**v0.5 新增：HR沟通**——把招聘方发来的消息粘贴进来，JobAgent 帮你读懂对方在问什么、
列出待办、并起草一条**可编辑**的回复。BOSS 沟通扫描因真实站点风控已暂停，当前控制台
和扩展均不提供打开、遍历或扫描 BOSS 消息页的入口。它不后台监控，也不会替你发送消息——
回复由你复制后自行发出，再回来标记。

**v0.4：投递队列**——AI 给建议，你做决定。队列告诉你「今天该投哪些」，
你在招聘平台上完成真实投递后回来点「标记已投递」，之后再逐步记录 HR 回复、面试、Offer。
完全手动投递和回来标记的原流程仍然保留。另有 M6 逐岗位双重人工确认入口；
自动/无人值守/批量投递、自动生成确认、自动重试与任何后续消息永远不在授权范围内。

**v0.3：快速采集（推荐的导入方式）**——在你平时用的 Chrome / Edge 里正常浏览招聘网站，
复制职位内容或截图，粘贴到 JobAgent 即可导入。JobAgent **不控制你的浏览器、
不访问招聘网站、不注入脚本、不读取 Cookie**，只处理你主动交给它的内容。
这是目前最通用、最可靠的导入方式，见 [第 6 节](#6-使用流程)。

v0.2 的**浏览器采集**仍然保留，但许多招聘网站会拒绝向自动化浏览器返回内容，
见 [已知限制](#9-已知限制)。

**新增（POC）：Chrome 扩展页面检测**——在你平时用的、已经登录的 Chrome 里，
打开一个 BOSS 页面后点一下扩展，把结构化岗位信息交给本机 JobAgent。
**只读、只在你点击时读一次**，不自动搜索、不翻页、不投递、不发消息，
也不读取任何 Cookie 或登录信息。这一阶段只是**可行性验证** ——
见 [`extension/README.md`](extension/README.md)。

## 2. 快速开始（Windows PowerShell）

在仓库根目录依次执行：

```powershell
.\scripts\dev.ps1 setup
```

```powershell
.\scripts\dev.ps1 seed
```

```powershell
.\scripts\dev.ps1 start
```

日常使用不需要再打开两个终端：直接双击仓库根目录的
`Start-JobAgent.cmd`，它只在服务尚未运行时启动本地后端和前端，等待健康检查通过后自动打开
`http://127.0.0.1:5173/#/console`。重复双击会复用现有服务，不会重复启动。需要关闭由该入口
启动的服务时，双击 `Stop-JobAgent.cmd`；它只停止自己记录的监听进程，不会关闭其他 Python
或 Node 程序。首次安装依赖仍需运行一次 `.\scripts\dev.ps1 setup`。

**改后端代码时加 `-Reload`。** 默认不开：只是运行 JobAgent 的人不需要一个文件监视器。
但后端启动后会一直跑它启动时的那份代码——改动已经落盘、构建过、测试过，运行中的后端
依然感知不到，看起来就像功能坏了而不是进程旧了。

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\launch-console.ps1 -Reload
```

商用分支仍提供过渡性的 `Start-JobAgent-Commercial.cmd`：先在 `frontend` 目录执行一次
`npm run build`，之后它只启动 FastAPI 一个进程，由后端直接提供已构建前端，日常运行不需要
Node；数据默认写入 `%LOCALAPPDATA%\JobAgent`，不会写入源码或提交到 Git。这仍是 P2 的运行
基础，不是已签名安装器。详情见
[`docs/product/WINDOWS_PACKAGING.md`](docs/product/WINDOWS_PACKAGING.md)。

P2C-A 还提供可重复构建的**未签名 Windows x64 当前用户级安装候选**。它把已审计的 P2B bundle
编译为单个安装 EXE，最终用户运行时不需要安装 Python/Node；支持开始菜单、覆盖升级和默认保留
本地数据的卸载，并生成 SHA-256 与候选 manifest。扩展目前仍需手工加载，Windows 安装器尚未代码
签名、确认适用的 Inno Setup 商业许可或通过无开发工具链的独立 VM 验收，因此不能当作正式商用
安装包。P2C-A3 已准备可复现的 Chrome Web Store ZIP、最小权限 manifest、自有图标与隐私/权限披露
草案，但尚未上传或审核；说明见
[`docs/product/CHROME_WEB_STORE_SUBMISSION.md`](docs/product/CHROME_WEB_STORE_SUBMISSION.md)。

可随时执行不含密钥的运行自检：

```powershell
cd backend
.\.venv\Scripts\python.exe -m app.cli doctor
```

然后打开 <http://127.0.0.1:5173>。

- `setup`：创建 `backend\.venv`、安装后端依赖与前端依赖，并在缺失时用
  `.env.example` 生成 `.env`。
- `seed`：创建 `data\jobagent.db` 并写入 6 条**虚构的演示岗位**（标记
  `[演示数据]`，非真实招聘信息）。
- `start`：在两个新的 PowerShell 窗口里分别启动后端与前端。关闭窗口即停止。

想在当前窗口里跑单个服务，加 `-NoNewWindow`：

```powershell
.\scripts\dev.ps1 backend -NoNewWindow
```

## 5. 配置 OpenAI API Key

Key **只**放在项目根目录的 `.env` 文件里，后端进程读取，前端永远拿不到。

1. 复制 `.env.example` 为 `.env`（`setup` 已自动完成）。
2. 用编辑器打开 `.env`，在 `OPENAI_API_KEY=` 后面填入你的密钥。
3. 重启后端。

```powershell
notepad .env
```

`.env` 已在 `.gitignore` 中，不会被提交。

确认是否生效（不会显示密钥本身）：

```powershell
.\scripts\dev.ps1 info
```

**没有配置 Key 时应用照常启动**：仪表盘、岗位库、简历、策略页面都能正常使用，
只有 AI 分析接口会返回一条明确的配置错误（HTTP 503），而不是让整个应用崩溃。

### 环境变量

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `OPENAI_API_KEY` | 空 | 必填才能使用 AI 分析 |
| `OPENAI_MODEL_FAST` | `gpt-5.6-luna` | 批量分析用的默认模型 |
| `OPENAI_MODEL_SMART` | `gpt-5.6-terra` | 「高质量重分析」专用，不会自动调用 |
| `DATABASE_URL` | `sqlite:///./data/jobagent.db` | 相对路径以仓库根目录为基准 |
| `MAX_ANALYSES_PER_RUN` | `50` | 一次批量分析的上限 |
| `AUTO_APPLY` | `false` | 保留兼容字段；没有全局自动投递模式 |
| `HUMAN_CONFIRMED_APPLY_ENABLED` | `false` | 开放 M6 单岗位双重人工确认入口；不代表任何岗位已获批准 |
| `BROWSER_CHANNEL` | `auto` | `auto`/`chromium`/`msedge`/`chrome` |
| `BROWSER_SUPPORTED_HOSTS` | `zhipin.com` | 允许采集的站点域名 |
| `QUICK_CAPTURE_AI_EXTRACTION` | `true` | 关闭后仍可本地解析文字，截图识别不可用 |
| `QUICK_CAPTURE_MAX_IMAGE_MB` | `10` | 截图上传大小上限 |
| `DAILY_APPLICATION_TARGET` | `10` | 每日投递目标，仅作参考，不会限制你 |
| `REPORT_TIMEZONE` | `Asia/Tokyo` | 「今日」类指标按这个时区计算 |
| `QUICK_CAPTURE_MAX_IMAGE_MB` | `10` | HR沟通截图沿用同一上限 |
| `RESPONSE_MATURITY_DAYS` | `7` | 超过这么久还没回复才算「成熟样本」 |
| `INTERVIEW_MATURITY_DAYS` | `14` | 面试率使用的更长成熟期 |
| `ANALYTICS_MIN_SAMPLE` | `5` | 低于这个样本量一律标注「样本不足」 |
| `ANALYTICS_RECOMMEND_SAMPLE` | `8` | 低于这个样本量不会给出可执行的策略建议 |
| `OFFER_DECISION_MIN_COVERAGE` | `0.7` | 信息覆盖率低于此值时，Offer 比较不给出综合结论 |

## 6. 使用流程

1. **简历**：上传 PDF / DOCX（也支持 TXT）。解析在本地完成，不调用 AI。
   页面会显示识别到的技能、证书、章节与文本预览。
2. **岗位库 → 添加岗位**：粘贴 JD 原文，填公司、职位、城市、薪资等。
   原文完整保留；系统只做空白与符号项目的规范化，并据此计算去重哈希 ——
   同一份 JD 重复粘贴会被拒绝，并告诉你已有岗位的编号。
3. **AI分析**：结合当前简历与求职策略给出匹配分与结论。结果会缓存，
   重复点击不消耗额度。缺薪资的岗位建议**先回填薪资再分析** —— 薪资是打分输入之一；
   若先分析后回填，该岗位基于旧薪资的分析缓存会被自动作废，需要重新分析。
4. **高质量重分析**：显式使用 `OPENAI_MODEL_SMART` 再跑一次（单独缓存）。
5. **岗位详情**：查看各维度分数、匹配/缺失技能、优势、不足、风险、分析摘要，
   以及一条中文招呼语（带复制按钮）。**系统不会自动发送任何消息。**
6. **状态跟踪**：待处理 / 已查看 / 已收藏 / 已跳过 / 已投递 / 已回复 /
   面试中 / 已offer / 已拒绝，每次变更都会写入操作记录。岗位已处于某个状态时，
   对应按钮会禁用 —— 重复提交同一状态只会返回 200 且什么都不做。
7. **批量 AI 分析**：勾选岗位（可「全选当前」，或「筛选并全选未分析岗位」——
   它会先把列表筛成未分析再全选，因为按匹配分排序时未分析岗位排在最后，
   容易被分页截掉），再点「批量 AI 分析」。确认弹窗会先显示选中数量、
   已命中缓存数、**预计新增 AI 调用次数**、批次上限 `MAX_ANALYSES_PER_RUN`
   与超出上限被推迟的数量；只有点确认才会花钱。失败的岗位只报告，不自动重试。
8. **删除岗位**：每行都有「删除」，会连带删除该岗位的分析结果与事件记录，
   删除前需要确认，且无法恢复。
9. **投递队列 → 去投递**：每条推荐都有「去投递 ↗」，会在新标签页打开岗位原页面
   并把招呼语放进剪贴板；你在招聘平台自己粘贴、检查、点发送。发送后回到队列点
   「标记已投递」并选择本次实际使用的简历，才会写入投递记录。
   你也可以对一个岗位使用 M6：明确接受 BOSS 将动态发送 JobAgent 无法预览、核实或控制的
   首次招呼语，生成只读快照后再次最终确认，扩展才会核对岗位身份并尝试点击一次「立即沟通」。该入口
   默认关闭；不批量、不后台、不自动重试，也不发送任何后续消息。站点结果无法可靠核实时，
   只记录「结果待确认」，不会自动标记已投递。

### 投递队列（v0.4）—— 每天的主界面

**推荐的日常流程：**

1. 「快速采集」导入职位。
2. 点「AI分析」。
3. 打开「投递队列」，看今天该投什么。
4. 逐条查看推荐理由、匹配/缺失技能。

> **JobAgent 不会自己投递简历，也不会向招聘方发送消息。**
> 「已投递」只是你告诉它：这件事我在招聘平台上已经做了。

队列里每个岗位可以：

- **标记已投递** —— 需要二次确认，不支持批量（因为它代表一次真实的外部行为）
- **稍后处理** —— 暂时移出队列，到期自动回来；不改变岗位状态
- **跳过** —— 可选原因（薪资太低 / 经验要求过高 / 外包驻场 …），随时可以恢复

筛选：城市、AI 结论、最低匹配分、状态、关键词，以及「包含 Maybe」（默认不含）。
排序：推荐优先（默认）、匹配分、最新、薪资。

**AI 结论 ≠ 你的状态**：AI 说「不建议」只是不把它放进队列，
**不会**把岗位标成已跳过。要不要跳过，永远由你决定。

「今日已投 4 / 10」只是参考信息（`DAILY_APPLICATION_TARGET`），
达到之后不会有任何限制或催促。日期按 `Asia/Tokyo` 计算，不会在 UTC 午夜错位。

### Offer 与谈薪（v0.9）

把「拿到 Offer 了」这一条记录，变成可比较的结构化薪酬与完整谈薪过程。

#### 工作流

1. **在外部收到 Offer**（邮件、电话、招聘平台）。
2. 在岗位详情页点「**记录 Offer**」，填入币种、薪酬明细与决定截止时间。
   可以粘贴 Offer 原文让系统识别金额 —— 识别结果只是建议，**你填的数值始终优先**，
   原文会完整保留。
3. 打算谈薪时，点「**记录我的诉求**」写下你要求的条件。
4. 对方回复后，点「**记录公司调整**」填入公司实际给出的新条件。
5. 需要时重复 3–4，历史记录不会被覆盖。
6. 在「**Offer**」页勾选 2–4 个 Offer 并列比较。
7. 明确点「**接受**」或「**拒绝**」，两者都需要确认。
8. 之后可在「Offer 分析」里查看转化、薪酬中位数与谈薪变化。

> JobAgent **不会**替你谈判、答复、接受或拒绝任何 Offer，也不接日历和邮箱。
> 这里记录的全部是你自己已经做出的决定。

#### 「公司的 Offer」和「我的诉求」不是一回事

这是这一版最重要的区分。假设：

```
公司初始 300K → 我方要求 350K → 公司调整到 330K
```

**公司当前的 Offer 是 330K，不是 350K。**
你提出的要求会单独显示为「我方诉求」，永远不会被当成对方给的条件，
也不能针对它点「接受」。

#### 薪酬是怎么算的

| 指标 | 含义 |
| --- | --- |
| 基础年薪 | 年薪；填了月薪和「几薪」会自动折算 |
| 首年保证现金 | 基本工资 + **保证**奖金 + 各类补贴 + 签字费 |
| 首年目标现金 | 上面再加上**目标**奖金 —— 这不是到手的钱 |
| 常态保证现金 | 第二年起，**不含**一次性签字费 |
| 估算总包 | 目标现金 + 折算后的股权 |

几条刻意的规则：

- **目标奖金不会被算成保证收入。** 两个数字并列显示，不会合成一个「总包」。
- **签字费只算首年。** 把一次性收入摊到每一年会永久高估这个 Offer。
- **股权不等于现金。** 只有同时填了股权价值和归属年限才会折算；
  否则显示「未计入可比较总包」，而不是当成 0 或按一年归属去猜。
- **没填 ≠ 0。** 留空表示「未知」，不会被当成零参与计算。
- **福利不会被折算成钱。**「公司提供宿舍」除非你自己填了估值，否则不进现金。

#### 不同币种不会被自动换算

400K CNY 和 8M JPY 会按**原币种**分别显示。
系统不会去查任何汇率。想跨币种比较，需要你在「决策分析」页
**自己填一个汇率**（见 [v1.0](#offer-决策分析v10)）；不填就不换算。

#### 条件对照页不会给出「哪个更好」

「条件对照」并列显示各项条件 —— 现金、股权、远程、地点、入职时间、福利，
**不会**合成综合评分。需要评分请用「决策分析」，那里的权重由你设定。

#### 接受之后就不会再变

点「接受」时，系统会记下**当时那一版**的薪酬。
之后再补充或更正记录，都不会改变你当初是基于什么做的决定。

#### 拒绝 ≠ 被拒

你主动拒绝 Offer 会记录为你的决定，并可选填原因，
统计里和「被对方拒绝」完全分开。

#### 截止日期

Offer 页会标注「今天截止 / 明天截止 / 3天内 / 已过截止日期」，按
`REPORT_TIMEZONE`（默认 Asia/Tokyo）计算。
过了截止日期系统**不会**自动作废该 Offer —— 只会如实显示，
是否失效由你确认。也不会发送任何提醒。

### Offer 决策分析（v1.0）

手上同时有几个 Offer 时，「哪个更好」不是一个能替你回答的问题 —— 但
「按你自己说的标准算，哪个分高」是可以算清楚的。这一页做的就是后者，
而且把算式全部摊开。

**本页不调用 OpenAI，一次都不会。**

#### 工作流

1. 在「**Offer**」页勾选 2–4 个 Offer，点「**决策分析**」。
2. **设定权重**：11 个维度各拖一个 0–10 的滑块。只看比例 ——
   5/3/2 和 50/30/20 完全一样，系统会自动归一化。设成 0 表示不在意。
3. 可选：设定**硬性条件**（最低保证现金、必须签证支持、必须远程/混合、
   指定城市、最晚入职日期）。
4. 跨币种时填写**汇率**。系统不联网、不查行情。
5. **给每个 Offer 打分**（1–5）。薪酬、远程、签证三项会自动从已记录的
   数据推导，其余维度需要你自己判断。
6. 看结果，需要的话点「**保存决策记录**」把这次比较冻结下来。

#### 综合评分是怎么算的

```
某维度贡献 = 归一化权重 × 该维度得分(0–1)
综合评分   = Σ贡献 ÷ Σ已知维度的权重
```

页面上每个维度的权重、得分和贡献都会列出来，合计也会列出来 ——
**任何时候都不会只给你一个孤零零的总分**。

几条刻意的规则：

- **没设权重就没有评分。** 全 0 或没填时系统不会假设一个「平均分配」，
  它没有资格替你决定什么重要。
- **没填 ≠ 0 分。** 没打分的维度会被**排除**在计算之外，既不加分也不扣分，
  只会拉低「信息覆盖率」。
- **覆盖率不够就不下结论。** 任一 Offer 的加权覆盖率低于 70%
  （`OFFER_DECISION_MIN_COVERAGE`），页面照常显示所有分数，但**不会**
  指出哪个最好。打平也一样。
- **截止时间不影响评分。** 明天截止只是**急**，不代表**好**。
  剩余天数单独显示，绝不进入分数。
- **AI 不给任何公司打分。** 主观评分完全由你填，留空就是留空。
- **薪酬只看公司给的那一版。** 你的谈薪诉求（candidate counter）永远不会
  被当成公司的 Offer；已接受的 Offer 读取接受时冻结的那一版。
  保证现金的权重是目标现金的 4 倍，无法折算的股权不计入。

#### 硬性条件只标记，不排除

每个硬性条件会显示 **满足 / 不满足 / 未知** 三种状态之一。
「未知」表示相关信息没记录过 —— 那不等于不满足。
不满足的 Offer 仍然会正常参与比较并显示分数，**系统不会自动淘汰任何 Offer**。

#### 汇率由你填

跨币种比较需要你自己填 `1 外币 = ? 基准币种`。
系统**不获取任何实时汇率**。不填就不换算 ——
该 Offer 的薪酬维度会被标为「无法比较」，而不是按某个猜出来的汇率折算。
保存决策记录时会把**当时用的那个汇率**一并冻结。

#### 决策记录会被冻结

保存后，这条记录里的 Offer、所用的薪酬版本、权重、评分、汇率、硬性条件
和结论**整体固定**。之后你改权重、改评分、公司调薪，都不会改变它。
一个过去的决定，应该能用你当时掌握的信息解释清楚。

#### 接受一个不会自动拒绝其他

点「接受」时，如果还有其他待决定的 Offer，页面会**列出来提醒你**，
但不会阻止你接受，**也不会替你拒绝任何一家**。
逐个答复是你的事，而且往往有先后顺序。

#### 谈薪定位

在决策分析页可以为每个 Offer 填「理想线 / 目标线 / 最低接受线」，
Offer 详情页会显示公司当前 Offer、我方最近诉求和两者差距。
低于最低线只会**提示一句**，不会自动拒绝 —— 低于你的线是否还值得考虑，
不是算术能回答的。

#### 隐私

权重、1–5 评分、汇率、谈薪目标、决策备注和硬性条件的数值
**都不会写进日志**。日志里只有 id 和数量。

   填入轮次类型和时间（只有轮次类型是必填的）。
3. **每轮面试结束后**点「记录结果」：通过 / 未通过 / 结果待定。
4. **继续添加下一轮**，直到流程结束。
5. 未通过时可以填写原因，并分别记录
   **面试官说了什么**（反馈）和 **你自己的复盘**（备注）—— 两者分开存储，
   统计只使用你勾选的标签，不会去解读任何自由文本。
6. 打开「面试」页查看即将进行、结果待定和已完成的流程。
7. 打开「面试分析」查看阶段转化、各轮通过率、淘汰节点与耗时。

#### 面试归属

一个面试流程属于**某一次具体的投递**（`applied_event_id`）。
如果一个岗位投过 → 恢复待处理 → 又投了一次，那是两次投递，
面试只属于其中一次；用哪份简历的功劳也随之确定，
**不会**因为你之后换了「当前AI分析简历」而改变。

#### 主动终止 ≠ 被拒

接受了别的 Offer、薪资谈不拢、自己不想去 —— 这些都记录为
**主动终止**，统计里和「被对方拒绝」分开显示。
你自己的决定不会被算成失败。

同样地，「结果待定」不等于「未通过」：还没出结果的轮次不会计入通过率的分母。

#### 已通过的轮次不会被抹掉

在终面被拒，前面通过的四轮依然完整保留 —— 流程会记录
「结束于终面」，而不是把这次候选经历归零。

#### HR 消息里的面试时间

「HR沟通」里的 AI 分析可以识别出对方提议的时间，但它**只会给出建议**。
系统不会替你创建面试、不会替你接受邀请、也不会回复对方。
你确认后，才会真正创建一轮面试。

#### 旧版面试记录

v0.8 之前记录的面试只是一条「面试」事件，没有轮次信息。
升级**不会**给它们编造 HR / 技术面 / 终面 —— 它们会在「面试」页
单独列出，并且不计入任何阶段统计。你可以手动补充轮次。

#### 关于费用与集成

面试功能和面试分析**完全不消耗 AI 额度**。
JobAgent 不接入日历、不接入邮箱、不会自动接受面试、不会自动回复招聘方 ——
所有面试信息都由你手动记录。

> 会议链接可能包含访问令牌，因此只会在面试详情页显示，
> 不会写入日志，也不会出现在任何统计数据里。

### 简历版本与简历表现（v0.7）

回答「哪一份简历真的更有效？」—— 用真实投递结果，而不是感觉。

**核心规则：归属以「投递当时记录的简历」为准。**
8月20日用 A 简历投了某岗位，8月25日你把 B 设为当前分析简历，9月1日拿到面试 ——
这个面试算在 **A** 头上，永远不会变。系统不会用「现在哪份简历是当前的」去倒推历史。

#### 两个「当前简历」，不要混淆

| 概念 | 含义 |
| --- | --- |
| **当前AI分析简历** | 新采集的岗位用哪份简历做匹配分析 |
| **本次实际投递简历** | 某一次投递你实际提交的是哪份 |

切换前者不会影响任何一条历史投递的归属。

#### 工作流

1. 在「简历」页上传或用「复制为新版本」建立多个版本，并命名
   （例如 `Cloud版` / `DevOps版` / `基础设施版`）。
2. 用一份或多份简历分析岗位。岗位详情页有「按此简历分析」与「比较简历」。
3. **真正投递后**，在「确认已投递」对话框里选择你**实际使用**的那份简历。
   不确定就选「不确定」——系统不会替你猜。没投简历（纯沟通）也可以如实记录。
4. 照常记录 HR 回复、面试、Offer。
5. 打开「简历表现」查看各版本的成熟回复率与面试率。
6. 谨慎对待小样本：2/2 = 100% 会被明确标注「样本不足」并排在最后。

#### 归属覆盖率

页面会显示「32 / 38 次投递已记录简历（84%）」。
覆盖率低于 60% 时，系统**不会**给出哪份简历更好的结论 ——
缺失太多时，比较本身就不可信。

#### 历史数据的限制

v0.7 之前的投递记录里没有简历信息，升级**不会**给它们补上。
用当前简历去回填等于凭空编造历史。它们会一直显示为「未记录简历」，
你可以在「简历表现 → 补充历史简历」里手动补齐 —— 只有你知道当时投的是哪一份。
补充会追加一条记录，原始投递事件不会被改写。

#### AI 匹配分 ≠ HR 反馈

「简历对比」显示同一份 JD 在不同简历下的匹配分，这是**模型判断的契合度**；
「简历表现」显示的是**招聘方的真实反应**。两者分开展示，因为它们经常不一致：
一份简历可能更讨 AI 喜欢，却收到更少回复。

#### 关于费用

「简历表现」和所有统计**不消耗任何 AI 额度**。
只有「比较简历」「按此简历分析」在遇到**尚未分析过**的组合时才会调用 API，
并且会先提示「将分析 N 份尚未分析的简历版本，可能产生 API 费用」，确认后才执行。
已分析过的组合直接读缓存。

> 这是**观察性数据**，不是随机 A/B 实验。不同简历常被用在不同城市、不同类型、
> 不同薪资区间的岗位上，这些差异都会混进结果里。因此页面只说
> 「某版本在已记录样本中的回复率更高」，不会说「某版本带来了更高的回复率」。

### 策略分析（v0.6）

「哪一类岗位对我真的有效？」—— 用你自己的投递结果回答，而不是靠感觉。

**完全不消耗 AI 额度**：这一页的每个数字都是对你已有记录的统计，可以随便刷新。

打开「策略分析」，可以按时间窗（7 / 30 / 90 天 / 全部）、城市、方向、来源筛选，
看到按城市、方向、城市×方向、来源、匹配分段、AI 建议、薪资区间拆分的转化表现，
以及 HR 最常问的问题、回复速度中位数和数据质量面板。

这一页的三条原则：

1. **刚投递的岗位不算「没回复」。** 只有已经收到回复、或者超过
   `RESPONSE_MATURITY_DAYS`（默认 7 天）的投递才算「成熟样本」，
   回复率的分母只用成熟样本。面试率用更长的 `INTERVIEW_MATURITY_DAYS`（默认 14 天）。
2. **不会出现光秃秃的百分比。** 每个比例都带着分子、分母和 95% 置信区间。
   分母为 0 时显示「—」，而不是伪造一个 0%。
3. **小样本不会因为运气好而排到第一。** 排序先看样本是否充足，再看置信区间下界。
   「广州 2/2 = 100%」会被明确标注「样本不足」并排在后面 —— 但仍然会单独提示你，
   因为这正是最容易被误读的一行。

#### 策略建议：系统建议，你来决定

```
数据观察   ->   系统建议   ->   你确认后才修改
```

只有同时满足「成熟样本 ≥ `ANALYTICS_RECOMMEND_SAMPLE`（默认 8）」「置信区间下界
高于整体水平」「置信度不是『样本不足』」三个条件，系统才会给出可执行的建议；
达不到就只会说「继续积累数据」。**因此经常没有任何建议，这是正确结果，不是故障。**

看建议、点「查看修改内容」都**不会写任何东西** —— 会先把
`career_strategy.yaml` 修改前后的完整内容摆给你看，你点「应用修改」之后才真正写入，
同时记录一条变更审计。点「暂不调整」会记住这条建议，之后不再打扰；
只有当证据发生实质变化时，它才会重新出现。

调整的只是**优先级顺序**，不会删掉任何城市，不会改变任何岗位的状态，
更不会去投递或发消息。

> 这里给出的是**相关性，不是因果**。「杭州回复率高」不等于「因为在杭州所以回复率高」——
> 也可能只是你在杭州投的岗位更匹配。样本少的时候，差异很可能只是运气。

仪表盘上也有一个精简的「求职策略表现」卡片；样本不够时它会直接说「数据积累中」，
而不是给你一个好看的数字。

### 求职策略

「什么是好岗位」由本机 gitignored 的 `data/career_strategy.yaml` 定义 —— 目标城市、目标岗位
方向、相关技能、排除关键词、经验与薪资偏好。可以在「求职策略」页面编辑并保存，
也可以直接改 YAML 文件（后端按文件修改时间热重载）。

策略是分析缓存键的一部分：改了策略，已分析的岗位下次会重新分析。

### 匹配分是怎么来的

分数不是模型随口给的：系统先做**确定性预分析** —— 城市命中、岗位名称命中、
技能重合（含别名，如 K8s → Kubernetes）、排除关键词命中、从 JD 中提取经验年限、
解析薪资区间，并算出一个透明的启发式基线分。模型拿到这些事实之后再做语义判断，
返回结果后还会经过一层护栏：所有分数裁剪到 0-100；命中排除关键词且技能重合明显
不足的岗位按策略上限封顶并强制 `skip`。

岗位详情页会同时显示模型分与基线分，方便你判断模型偏离机械信号多远。

分数区间参考（不机械套用）：

| 分数 | 含义 |
| --- | --- |
| 90-100 | 非常匹配，强烈建议投递 |
| 80-89 | 匹配良好，建议投递 |
| 70-79 | 基本匹配，有差距但值得投 |
| 60-69 | 边缘岗位，可投可不投 |
| < 60 | 通常不建议投递 |

3-5 年经验的岗位不会被自动否决；只有 JD 明确写出硬性门槛时，年限才被当作硬性条件。

## 9. 已知限制

> 提示：本节的限制只影响 **v0.2 浏览器采集**。
> **v0.3 快速采集不受影响**，因为它根本不控制浏览器，推荐优先使用。

**BOSS 直聘目前不会向自动化浏览器返回页面内容。**
实测：由 Playwright（CDP）控制的浏览器打开 zhipin.com 后，页面会在几秒内被置为空白，
而同一浏览器打开其它网站一切正常。这是招聘网站自身的反自动化措施。

本项目**不会**绕过它——不做 stealth、不伪造指纹、不隐藏 `navigator.webdriver`、
不破解验证码。遇到这种情况，应用会明确提示：

> 招聘网站没有向自动化浏览器返回页面内容（页面为空白）。本工具不会绕过此类限制，
> 请改用「岗位库 → 添加岗位」手动粘贴 JD。

因此在当前状态下：

- 采集**管线**（选页 → 提取 → 规范化 → 去重 → 入库 → AI 分析）已完整实现，
  并针对贴近真实结构的本地 HTML 做了完整测试；
- 但**对线上 BOSS 的实际采集会被网站拦截**，暂时仍需手动粘贴 JD；
- 若日后网站策略变化，或换成不做此类拦截的站点，同一套代码即可直接工作；
- **现在的推荐做法是使用「快速采集」**，它完全绕开这个问题。

其它限制：

- 浏览器采集只支持 BOSS（`zhipin.com`）；快速采集则不限站点。
- 「已投递」「已回复」等状态完全依赖你手动记录；
  JobAgent 无法知道你在招聘平台上做了什么。
- HR沟通不是自动收件箱：没有自动收信、轮询或发送能力。BOSS 沟通扫描已暂停，
  当前消息只能由你主动粘贴；不会自动同步 HR 回复。
- 对话发言人识别是尽力而为；粘贴整段对话时建议用「HR：」「我：」标注，
  识别不确定时会给出提示并保留原文。
- 时间线上的时间戳按**浏览器所在时区**显示，而「今日」类统计按后端的
  `REPORT_TIMEZONE`（默认 Asia/Tokyo）计算。两者在日本本地使用时一致。
- 快速采集的本地规则解析针对中文招聘网站的常见排版，遇到很不规则的排版时
  某些字段可能识别不出来——预览页面里可以直接手动补齐。
- 剪贴板按钮依赖浏览器的 Clipboard API。`127.0.0.1` 是安全上下文，
  正常可用；若浏览器拒绝授权，会提示改用 `Ctrl+V`。
- 选择「当前岗位」依据的是**最近一次发生导航的受支持标签页**。
  Playwright 会关闭后台节流，导致所有标签的 `document.visibilityState` 都是
  `visible`，无法据此判断前台标签。采集前请确认页面上显示的 URL 是你要采的那一个。
- 扫描件 PDF 简历需要先自行 OCR。
- Offer 信息全部靠手动记录：不接邮箱、不接日历，忘记记录就不会出现在统计里。
- 不同币种不做换算，因此跨币种的 Offer 无法直接比较总额。
- 股权只有在填了价值和归属年限时才会折算；期权的实际价值本就无法确定。
- 薪酬识别只读取基本工资类的数字，奖金和股权需要手动填写。
- Offer 样本通常很少，薪酬中位数与转化率的置信区间会很宽 ——
  页面会标注样本量，请照着样本量读。
- v0.9 之前的 Offer 记录只有一个金额字符串，不会被自动转成结构化 Offer。
- 一次投递只能有一个 Offer；同一岗位重新投递则是新的一次。
- 面试信息全部靠手动记录：不接日历、不接邮箱，忘记记录的面试不会出现在统计里。
- v0.8 之前的面试事件没有轮次信息，不会被自动分类，也不计入阶段转化。
- 面试阶段统计基于你记录的轮次，而不是岗位状态。
- 一次投递只能有一个面试流程；如果同一岗位重新投递，那是新的一次流程。
- 面试样本通常比投递样本小得多，阶段转化率的置信区间会很宽 ——
  页面会标注样本量，请照着样本量读。
- 简历比较是观察性的，不是随机实验。不同简历被用在不同岗位上，
  结果里混着岗位本身的差异。
- v0.7 之前的投递没有简历归属，只能手动补充，不会被自动回填。
- 「复制为新版本」复制的是内容与元数据，**不会**修改简历文字。
  v0.7 只做追踪与比较，不生成或改写简历。
- 内容完全相同的两个版本共用同一个分析缓存（缓存键基于内容哈希），
  因此它们在匹配分上不会有差别 —— 这是正确的，但矩阵里可能只有其中一个有分数。
- 已被投递记录引用的简历不能删除，只能归档。
- 策略分析给出的是**相关性**，不是因果。回复率受简历、投递时间、市场行情、
  甚至运气影响，这些都不在统计范围内。
- 分析只能看到**你记录过的动作**。忘记点「已投递」的岗位不会进入统计。
- 「来源」表示机会从哪里来，不代表 JobAgent 会去操作那个平台。
- HR 问题统计只覆盖你手动录入并分析过的消息，数据质量面板会显示覆盖率。
- 样本量小的时候，几乎所有维度都会显示「样本不足」。这是设计如此：
  与其给一个看起来确定的结论，不如老实说数据还不够。
- 决策评分只是**把你自己的偏好算了一遍**，不是对 Offer 好坏的客观判断。
  换一组权重就会换一个结论 —— 这正是它应有的样子。
- 薪酬维度是**相对**打分：以本次比较中最高的可比保证现金为满分。
  换一批 Offer 比较，同一个 Offer 的薪酬得分会变。
- 跨币种比较完全取决于你填的汇率是否合适。系统不获取、不校验、不更新汇率。
- 决策记录一旦保存就不可修改，也没有编辑入口 —— 想要新的结论请重新保存一条。
- 「我的评分」是主观的，而且往往是在信息不全的时候打的。
  覆盖率高不代表判断准，只代表填得多。
- Chrome 扩展目前是 **POC**：测试固件是照着 BOSS 的结构惯例手写的，不是真实 DOM
  的副本。测试通过只说明抽取器能处理这些形状，**不代表对线上 BOSS 一定有效**。
- 扩展不滚动也不点击，所以需要点「展开」或滚动后才渲染的职位描述会抽不到。
- 搜索结果卡片本身不含职位描述，只能预览，不能直接导入。
- BOSS 改版会让选择器失效。届时只需要改 `extension/src/boss/selectors.ts`，
  弹窗的开发者模式会告诉你是哪个字段先断的。

## 10. 安全与合规

- **快速采集只处理你主动提供的内容**：不抓取网站、不访问你填的链接、
  不使用浏览器扩展、不注入脚本、不连接 DevTools、不读取招聘网站的 Cookie
  或 localStorage、不自动登录。
- 剪贴板**只在你点击「读取剪贴板」的那一刻读取一次**，不做任何后台监听。
- 截图不落盘、不入库、不写日志，只保留哈希与结构化字段。
- API Key 只存在于后端：不进 React、不进数据库、不进日志、不从接口返回。
- **没有全局自动投递模式**。M6 只允许一个岗位经双重人工确认后尝试一次不可分割的首次招呼；
  无人值守投递、批量投递、自动生成确认、自动重试与任何后续消息均不被授权。
- **不**绕过验证码、反爬机制、登录保护或频率限制。
- **不**保存招聘网站的账号密码；登录完全由你本人在可见浏览器中完成。
- 浏览器 Cookie / localStorage 只留在本机的 `data/browser_profiles/`，
  **不会**通过任何接口暴露，也没有调试用的 cookie 接口。
- 不记录 Cookie、请求头、表单内容或整页 HTML；URL 记录时会去掉查询串
  （BOSS 会把会话令牌放在 `securityId`、`lid` 参数里）。
- 采集使用**独立的浏览器配置目录**，不会打开或占用你日常使用的浏览器配置。
- 简历原文只保存在本机 SQLite；调用模型时只发送结构化摘要与必要节选。
- 演示岗位为虚构数据，标记 `[演示数据]`，不得当作真实招聘信息。
- `backend/tests/fixtures/` 里的 HTML 为本项目手写的仿真结构，
  不是任何真实页面的副本，公司与岗位信息均为虚构。
